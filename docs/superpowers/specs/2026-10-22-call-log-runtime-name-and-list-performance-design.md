# 通话记录运行时名称与列表查询性能

日期：2026-10-22

## 目标

通话记录的“运行时”列优先显示通话开始时选用的实时模型配置名称；记录列表在对话文本较长、记录较多时仍能快速加载。保留现有筛选、页码及总数交互。

## 当前问题

- 实时配置表有自定义 `name`，但创建通话记录时只保存运行模式、提供商和模型 ID；页面因此只能显示提供商。
- 列表查询 `SELECT cl.*` 会把每条记录的完整 `transcript` 读出并发送给浏览器，即使用户未展开该记录。
- 列表按 `started_at DESC` 排序并使用 `LIMIT/OFFSET`；`call_logs` 没有对应索引。每次请求还会计算精确总数。

## 方案

### 运行时名称

给 `call_logs` 增加可空 `runtime_config_name`。新建实时通话时，从 Agent 当前绑定的 `realtime_configs.name` 取值并写入该列；不在列表查询时关联当前配置，避免配置改名、解绑或删除后篡改历史显示。Pipeline 通话保持空值。前端优先显示这个快照；旧记录没有快照时，依次回退到模型 ID、提供商、运行模式。模型 ID 仍保留在 API 字段中。

### 列表和展开

列表继续返回 `items`, `total`, `page`, `page_size`，但每条记录只查询表格及诊断所需的标量字段，不读取 `transcript`。`has_transcript` 在结束通话时与正文同步写入，旧记录在迁移时一次性回填，避免列表为判断“展开”而读取大段正文。对话内容通过管理员鉴权的单条记录详情接口在首次展开时读取，并按记录 ID 缓存在当前页面，翻页或刷新列表时清空缓存。详情读取失败时展示错误并允许重试，不把失败误显示成“暂无对话记录”。无正文但有失败诊断的记录仍可展开查看诊断；进行中的通话如果列表显示尚无对话及诊断，保持不可展开状态，重新加载列表后可更新。

### 查询与索引

在数据库迁移中增加按 `started_at DESC, id DESC` 排序的索引，以及针对 `status`、`agent_id`、`caller_user_id` 加时间/ID 后缀的索引。排序添加 `id DESC` 保证同时间记录的页间顺序稳定。精确总数查询保留，以维持当前页码与总页数；使用索引优化常见过滤，但不承诺极深页的 `OFFSET` 为常数时间。限制不合理的页码与页面大小，避免一次请求读取过多行。

## 验证

- 测试新实时通话写入名称快照，修改配置名称后历史记录不变；旧记录按模型 ID 回退显示。
- 测试列表无对话正文、详情可读取完整正文、鉴权及不存在记录的错误处理。
- 测试分页、筛选、稳定排序、总数，检查 SQLite 查询计划使用目标索引；用生成的大量测试记录对比列表载荷和查询时间。
- 运行后端测试及前端构建，并手动检查展开时加载、错误与重试状态。

## 不包含

不改为游标分页，不回填无法确定原配置名称的旧记录，不改变通话正文的存储格式。
