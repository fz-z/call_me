# 实时通话首句后自动退出修复设计

## 事件与证据

`3689e6a` 上线后，三次实时通话均收到千问首段音频且成功发布 LiveKit 音轨，却在约 1–2 秒后以 Worker 运行失败断开。输出任务没有记录“音频发布失败”警告。此前版本没有独立待播队列；本次新增的 5 秒 PCM 队列上限会在模型生成快于实际播放时抛出异常并结束会话。线上已临时恢复 `d70aad9` Agent 镜像；回退后一通电话有音频发布且以 completed 结束。现有失败日志只给通用错误分类，因此将 5 秒队列溢出作为最强假设，通过回归测试和上线后的安全分类日志确认，不能把它当作已实证的唯一原因。

## 方案

保持 WebSocket 接收与 LiveKit 播放分离、20 毫秒帧和 `speech_started` 立即取消/清空的打断路径。把正常音频的待播上限改为 60 秒 PCM16（约 2.88 MB/通话），允许模型短时超实时生成。若仍超过上限，不再使整个通话退出：记录固定的 `audio_backlog_overflow` 分类，丢弃当前回复后续音频直至 `response.done`，下轮回复恢复输出；不记录文字、音频、音色 ID 或密钥。保留 `response.done` 后已排队尾音，除非用户开口触发清空。

为其他实时失败增加固定枚举诊断：`audio_publish_failure`、`provider_error`、`connection_closed` 等，仅供日志和通话失败原因使用。不得输出原始供应商异常。对回退后的线上先运行完整测试、独立复核，再仅重建 Agent 容器。保留当前回退镜像为回滚点。

## 验证

测试先复现超过旧 5 秒但小于 60 秒的突发音频导致会话失败，再证明新版本保持连接且顺序播放；覆盖真正超过 60 秒时当前回复截断但会话和下一轮仍可用、打断仍会清除待播音频、队列字节数归零和关闭清理。用服务器无网络临时容器跑 Agent 全量测试。发布后观察 Worker 注册、重启次数及安全分类日志，并由真实通话验证首句、后续轮次和打断；未经真实通话，不宣称线上完全修复。
