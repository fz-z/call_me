# 首句打断修复设计

## 目标与范围

修复端到端千问通话中用户开口后首句仍继续播放的问题，同时让经典 Pipeline 的备用首句遵循 Agent 的“允许打断”开关。正常对话、声音复刻、管理后台及试听流程不变。管理员关闭打断时，继续保持当前不接受播报期间用户语音的行为。

## 已确认的现状

- 近期生产通话以 Qwen 实时模式为主，相关 Agent 的 `allow_interruptions` 为真。实时适配器使用 `server_vad`，麦克风音频在播报期间仍会传给供应商。
- Qwen 的 `input_audio_buffer.speech_started` 事件目前被忽略，LiveKit `AudioSource` 已缓存的旧回复音频也不会清空。供应商即使取消回复，用户仍可能听到剩余缓存。
- Pipeline 正常首句继承 `allow_interruptions`，但 LLM 首句生成失败时的备用 `session.say` 固定使用 `False`。
- 当前生产日志没有语音开始、响应取消这两类事件，无法回溯单次通话究竟在供应商检测还是本地播报处延迟。此次不记录音频、转写或密钥。

## 方案

采用供应商现有 `server_vad`，不新增客户端 VAD 或额外强制取消请求。实时适配器收到 `input_audio_buffer.speech_started` 时，仅在允许打断且有回复正在生成的情况下通知音频桥：立即清空本地 `AudioSource` 队列，并丢弃此旧回复随后到达的 `response.audio.delta`，直到对应 `response.done`。持续发送麦克风音频，后续新 `response.created` 恢复正常播报。若事件发生在非播报状态，不清空新一轮音频。`response.done` 即使未提供取消原因，也结束旧回复的丢弃窗口；连接关闭时清理状态。

桥提供单一的 `clear_output()` 接口，并与 `publish_pcm()` 共用输出锁，避免清队列与写音频竞态。若尚未创建输出源，清队列为空操作；若运行时音频源不支持清队列，应记录不含敏感数据的警告并保持通话运行。适配器日志只记录 VAD 语音开始、旧回复取消/结束和本地缓冲清空是否成功，不记录文字、音频或供应商标识。

经典 Pipeline 的备用问候语改为 `allow_interruptions=allow_interruptions`，其余首句路径不变。

## 验证与发布

先用确定性测试复现：旧音频已入队、收到语音开始、队列清空、旧增量不再播放、新回复可继续；覆盖关闭打断、非播报语音、输出源尚未建立、备用首句标志及资源清理。运行 Agent 全量测试并做源码检查。发布仅重建 Agent 容器，保留部署前 Git 提交和当前镜像作为回滚依据；真实通话分别测试首句和后续轮次，检查日志事件与听感。未经真实通话验证，不宣称线上打断问题已解决。
