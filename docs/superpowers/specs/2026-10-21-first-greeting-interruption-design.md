# 首句打断修复设计

## 目标与范围

修复端到端千问通话中用户开口后首句仍继续播放的问题，同时让经典 Pipeline 的备用首句遵循 Agent 的“允许打断”开关。正常对话、声音复刻、管理后台及试听流程不变。管理员关闭打断时，继续保持当前不接受播报期间用户语音的行为。

## 已确认的现状

- 近期生产通话以 Qwen 实时模式为主，相关 Agent 的 `allow_interruptions` 为真。实时适配器使用 `server_vad`，麦克风音频在播报期间仍会传给供应商。
- Qwen 的 `input_audio_buffer.speech_started` 事件目前被忽略，LiveKit `AudioSource` 已缓存的旧回复音频也不会清空。供应商即使取消回复，用户仍可能听到剩余缓存。
- Pipeline 正常首句继承 `allow_interruptions`，但 LLM 首句生成失败时的备用 `session.say` 固定使用 `False`。
- 当前生产日志没有语音开始、响应取消这两类事件，无法回溯单次通话究竟在供应商检测还是本地播报处延迟。此次不记录音频、转写或密钥。

## 方案

采用供应商现有 `server_vad`，不新增客户端 VAD 或额外强制取消请求。实时适配器收到 `input_audio_buffer.speech_started` 时，只要允许打断就清空尚未播完的本地音频；`response.done` 仅表示供应商生成结束，不代表本地已播完。若旧回复仍在生成，同时丢弃其随后到达的 `response.audio.delta`，直到对应 `response.done`。持续发送麦克风音频，后续新 `response.created` 恢复正常播报。即使用户在 `response.done` 之后开口，也清除可能残留的旧尾音，但不会丢弃新一轮回复。连接关闭时清理状态。

桥提供单一的 `clear_output()` 接口，并与 `publish_pcm()` 共用输出锁。供应商 WebSocket 接收协程不能等待可能阻塞的 LiveKit `capture_frame()`：适配器用独立的输出任务、最多 5 秒 PCM 的有界待播队列传送音频，每帧限制为 20 毫秒。打断时先取消输出任务并丢弃待播队列，再清 LiveKit 队列，避免较长音频片段在底层继续写入。若尚未创建输出源，清队列为空操作；若运行时音频源不支持清队列，应记录不含敏感数据的警告并保持通话运行。输出失败或待播队列超限明确终止会话而不是无限堆积。适配器日志只记录 VAD 语音开始、白名单化的回复状态和取消原因、本地缓冲清空是否成功，不记录文字、音频或供应商标识。

经典 Pipeline 的备用问候语改为 `allow_interruptions=allow_interruptions`，其余首句路径不变。

## 验证与发布

先用确定性测试复现：旧音频已入队、收到语音开始、队列清空、旧增量不再播放、新回复可继续；尤其覆盖 `response.done` 之后仍有本地尾音、LiveKit 写入阻塞但 VAD 事件仍须及时处理、长音频短帧拆分、关闭打断、输出源尚未建立、备用首句标志及资源清理。运行 Agent 全量测试并做源码检查。发布仅重建 Agent 容器，保留部署前 Git 提交和当前镜像作为回滚依据；真实通话分别测试首句和后续轮次，检查日志事件与听感。未经真实通话验证，不宣称线上打断问题已解决。
